# LINEシャトル報告連携 MVP仕様書

## 1. 文書の目的

本書は、バドミントン部のLINEグループに投稿されたシャトル残量報告を、シャトル管理システムへ自動登録するMVP（Minimum Viable Product）の仕様を定義する。

MVPでは、従来の報告方法をできる限り変えず、部員が次のようなメッセージを送るだけでシステムへ保存される状態を目指す。

```text
吹田ニュー2セミ3です。
```

## 2. 背景と課題

現在は、練習終了後に1回生の部員がシャトルの残量を数え、専用ではないLINEグループへ報告している。

対象となるシャトルは次の2種類である。

- ニュー：新品のシャトル
- セミ：ほぼ新品のシャトル

練習拠点は豊中と吹田の2拠点であり、残量は筒単位で報告する。満タンではないが1個以上シャトルが入っている筒は、現在の運用上 `0.5` として扱う。

現状には次の問題がある。

- LINEグループがシャトル報告専用ではなく、最新報告をすぐに見つけられない
- 前回残量を把握しにくく、数え間違いに気づきにくい
- 会計係が使用量の推移を把握しにくい
- 購入した箱数と、現在保有する筒数の関係を把握しにくい
- 現在のWebシステムは視認性がよい一方、従来と入力方法が異なり、報告者の負担が増える

## 3. MVPの目的

MVPの目的は次のとおりとする。

1. 部員が従来とほぼ同じ文章をLINEへ送信できる
2. 正しい報告をシャトル管理システムへ自動保存できる
3. 保存結果と前回との差をLINE上ですぐ確認できる
4. LINEの一般的な会話を誤って報告として登録しない
5. Webフォームからの既存の報告方法も引き続き利用できる

## 4. MVPの対象範囲

### 4.1 対象機能

- LINE Messaging APIのWebhook受信
- Webhook署名の検証
- 許可したLINEグループの判定
- シャトル報告メッセージの解析
- 報告内容の入力値検証
- Reportデータの新規登録
- 直前報告以降の購入・移動を反映した前回比の計算
- 登録結果のLINE返信
- 最新残量を確認するコマンド
- Webhook再送時の二重登録防止
- LINEメッセージ送信取消時のReport削除
- 誤報告を送信取消・再送、またはWeb履歴画面から訂正する運用
- LINE報告とWeb報告の識別
- 主要処理の自動テスト

### 4.2 MVPの対象外

次の機能はMVP完成後のフェーズで検討する。

- シャトル購入の登録
- 箱数から筒数への換算
- 拠点間のシャトル移動
- 月別・練習別の使用量グラフ
- 在庫下限通知
- LINEへの定期リマインダー
- リッチメニュー
- Web画面の認証・権限管理
- 報告者ごとの集計
- 正確なシャトル個数の記録

## 5. 用語と数値の扱い

| 用語 | 意味 |
| --- | --- |
| ニュー | 新品のシャトル |
| セミ | ほぼ新品のシャトル |
| 拠点 | 豊中または吹田 |
| 1筒 | 満タンのシャトル筒1本 |
| 0.5筒 | 満タンではないが、1個以上シャトルが入っている筒 |
| 報告 | 練習終了後に送信される拠点ごとの残量情報 |

`0.5` は実際の半筒を意味せず、端数筒が存在することを表す運用上の値である。このため、将来表示する使用量は概算値として扱う。

## 6. LINEメッセージ仕様

### 6.1 正式な報告形式

基本形式は次のとおりとする。

```text
{拠点}ニュー{ニュー残量}セミ{セミ残量}です。
```

例：

```text
吹田ニュー2セミ3です。
豊中ニュー2.5セミ1です。
```

### 6.2 許容する表記

入力負担を減らすため、次の表記揺れを許容する。

```text
吹田ニュー2セミ3です。
吹田ニュー2セミ3
吹田 ニュー2 セミ3
吹田　ニュー２　セミ３です。
豊中ニュー2.5セミ0
```

解析前に以下の正規化を行う。

- Unicode NFKC正規化により全角英数字を半角へ変換する
- 文字列の先頭と末尾の空白を除去する
- 項目間の半角・全角空白を許可する
- 文末の `です`、`。`、`.` は省略可能とする

### 6.3 数値ルール

- `0` 以上であること
- 整数または `0.5` 刻みであること
- `0`、`0.5`、`1`、`1.5` などを許可する
- 負数を拒否する
- `0.1`、`1.2` など、0.5刻みではない値を拒否する
- `NaN`、`Infinity` など、有限数ではない値を拒否する

### 6.4 報告解析結果

メッセージは次の4種類に分類する。

| 分類 | 条件 | 動作 |
| --- | --- | --- |
| `report` | 正しい報告形式 | DBへ保存して結果を返信する |
| `status` | `シャトル残量` または `残量` と一致 | 豊中・吹田の最新残量を返信する |
| `invalid-report` | ニュー・セミなどを含むが形式が不正 | 保存せず、正しい形式を返信する |
| `ignore` | 一般的な会話 | 保存せず、返信もしない |

一般会話を誤登録しないよう、報告形式はメッセージ全体が所定の形式に一致した場合のみ有効とする。

## 7. LINE返信仕様

### 7.1 登録成功時

登録後、同じLINEグループへ次の形式で返信する。

```text
✅ 吹田の残量を登録しました

今回
ニュー：2筒
セミ：3筒

前回比
ニュー：-1筒
セミ：+0.5筒
```

前回報告が存在しない場合は次のように表示する。

```text
✅ 吹田の残量を登録しました

ニュー：2筒
セミ：3筒

この拠点では最初の報告です。
```

前回比は、直前報告へ今回の報告日時までの購入とニュー・セミ移動を
反映した残量を基準として、ニュー・セミそれぞれの差を計算する。

### 7.2 不正な報告時

シャトル報告の意図があると判断できるが形式が不正な場合、保存せず次を返信する。

```text
⚠️ 登録できませんでした
「吹田ニュー2セミ3です。」の形式で送信してください。
数値は0.5刻みで入力できます。
```

### 7.3 最新残量の確認

ユーザーが次を送信する。

```text
シャトル残量
残量
```

Botは次の形式で返信する。

```text
🏸 現在のシャトル残量

豊中：ニュー3 / セミ2.5
吹田：ニュー2 / セミ3

最終更新：8月7日 18:42
```

一方の拠点に報告が存在しない場合は `報告なし` と表示する。

## 8. 保存仕様

### 8.1 Reportへ保存する情報

- 拠点
- ニュー残量
- セミ残量
- 報告日時
- 登録元（`WEB` または `LINE`）
- LINEメッセージID
- LINEグループID
- LINEユーザーID（Webhookに含まれる場合）
- 元メッセージ
- 作成日時
- 更新日時

報告日時には、サーバーがWebhookを受信した時刻ではなく、LINEイベントの `timestamp` を使用する。

### 8.2 既存Webフォームとの関係

- Webフォームからの登録機能は残す
- WebとLINEで入力値検証を共有する
- WebとLINEでReport保存処理を共有する
- Webから登録したReportは `source = WEB` とする
- LINEから登録したReportは `source = LINE` とする

## 9. Webhook処理仕様

Webhookは次の順番で処理する。

1. リクエスト本文を未加工の文字列として取得する
2. `x-line-signature` を検証する
3. 署名が正しい場合のみJSONへ変換する
4. イベント種別を確認する
5. LINEグループIDを確認する
6. `webhookEventId` の処理済み判定を行う
7. メッセージを解析する
8. DB transaction内でReportとWebhook処理記録を保存する
9. LINEへ結果を返信する
10. HTTP 200を返す

### 9.1 署名エラー

- `x-line-signature` がない場合は処理しない
- 署名が一致しない場合は処理しない
- HTTP 401を返す

### 9.2 Webhook URL検証

LINE Developers Consoleから送信される `events: []` の検証リクエストに対して、HTTP 200を返す。

### 9.3 二重登録防止

- `webhookEventId` を一意な値として保存する
- 処理済みの `webhookEventId` が再送された場合はReportを作成しない
- 再送イベントに対してもHTTP 200を返す
- 同時に同じイベントを受信しても、DBの一意制約により二重登録を防止する

## 10. 誤報告の訂正と送信取消

### 10.1 誤報告の訂正

MVPではLINEメッセージの編集機能に依存しない。誤った報告を送信した場合は、次のいずれかの方法で訂正する。

1. LINE上で誤ったメッセージを送信取消し、正しい内容を新しいメッセージとして送信する
2. 送信取消ができない場合は、Webの履歴画面から対象Reportを編集する

単に正しい内容を再送した場合、新しい報告が最新値として扱われるが、誤った報告は履歴に残る。そのため、原則として誤ったメッセージを送信取消してから再送する。

### 10.2 送信取消

LINEから `unsend` イベントを受信した場合、対象の `lineMessageId` を持つReportを削除する。

- 取消済みメッセージの本文を保持しない
- 削除後、各画面では次に新しいReportが最新値となる
- `unsend` イベントには返信しない

## 11. セキュリティ要件

- LINE Webhookは必ず署名を検証する
- 署名検証には未加工のリクエスト本文を使用する
- LINE PlatformのIPアドレスによる制限には依存しない
- 設定済みの `LINE_ALLOWED_GROUP_ID` と一致するグループだけを処理する
- 1対1トークや未許可グループからの報告は保存しない
- Channel secretとChannel access tokenをソースコードへ記載しない
- 秘密情報は環境変数で管理する
- `.env` をGitへコミットしない
- 本文やトークンを不要にログ出力しない

必要な環境変数は次のとおりとする。

```env
LINE_CHANNEL_SECRET=
LINE_CHANNEL_ACCESS_TOKEN=
LINE_ALLOWED_GROUP_ID=
APP_BASE_URL=
```

## 12. エラー処理

| エラー | 動作 |
| --- | --- |
| 不正署名 | HTTP 401、DB処理なし |
| 未許可グループ | HTTP 200、DB処理・返信なし |
| 一般会話 | HTTP 200、DB処理・返信なし |
| 不正な報告形式 | HTTP 200、DB保存なし、入力例を返信 |
| DB保存失敗 | HTTP 500を返し、Webhook再送の対象とする |
| DB保存成功・LINE返信失敗 | Reportは維持し、返信エラーをログへ記録する |
| 処理済みWebhookの再送 | HTTP 200、二重保存なし |

## 13. 非機能要件

- Webhookの通常処理は数秒以内に完了すること
- LINEの返信トークンを受信後1分以内に使用すること
- Webhook処理に失敗した原因をサーバーログから確認できること
- ログにChannel secretやChannel access tokenを出力しないこと
- 既存のWeb画面とAPIを壊さないこと
- データ取得を伴うWeb画面では、待機中であることが分かる表示を行うこと
- TypeScriptの型チェックに成功すること
- ESLintでエラーが発生しないこと
- production buildに成功すること

## 14. テスト要件

### 14.1 メッセージ解析テスト

- 正しい整数を解析できる
- `0` を解析できる
- `0.5` を解析できる
- 全角数字を解析できる
- 全角空白を解析できる
- 文末の `です。` がなくても解析できる
- 負数を拒否する
- 0.5刻みではない値を拒否する

- ニューまたはセミがない報告を拒否する
- 一般会話を `ignore` に分類する

### 14.2 Webhookテスト

- 正しい署名を受け付ける
- 不正な署名を拒否する
- 空のイベント配列へHTTP 200を返す
- 許可グループの報告を保存する
- 未許可グループの報告を保存しない
- 同じWebhookを再送しても1件だけ保存する
- 送信取消イベントで既存Reportを削除する
- 送信取消後に正しい報告を再送すると、新しいReportが登録される
- DBエラー時にHTTP 500を返す

### 14.3 既存機能の回帰テスト

- Webフォームから報告を登録できる
- ホームに各拠点の最新値が表示される
- 履歴を新しい順に表示できる
- 豊中・吹田で履歴を絞り込める
- 履歴からReportを編集できる

## 16. MVP完成後の拡張候補

MVP運用後に、実際の利用状況と部員・会計係の意見を確認してから次の機能を追加する。

1. 箱数と豊中・吹田への配分を含むLINEメッセージからの購入記録
2. 箱数から筒数への変換
3. 拠点間の在庫移動記録
4. 拠点別・月別の概算使用量グラフ
5. 残量下限通知
6. 練習終了後1時間以内に報告がない場合の報告忘れ通知
7. 会計係だけが編集できるWeb認証
8. 購入・移動履歴のWeb表示

報告忘れ通知は、グループ宛てのPush APIが送信対象人数分の月間メッセージ通数を消費し、無料プランの上限へ早期に到達する可能性が高いため、現構成では実装を見送る。少人数の通知先やLINE以外の通知手段を採用する場合に再検討する。

再検討する場合は、次の事項を決定する必要がある。

- 練習終了時刻をどこから取得するか
- 練習ごとの対象拠点をどのように判定するか
- 報告済みとみなす時間範囲と、通知を送る回数
- Push APIでグループへ送る通知の通数と、LINE公式アカウントの料金プランをどう管理するか

### 16.1 購入管理・拠点間移動（フェーズ9）

購入したシャトルは1箱10筒として扱い、共通倉庫は管理しない。購入時の保管先は、豊中・吹田への筒数配分を同じLINEメッセージへ記載して指定する。

購入メッセージの形式は次のとおりとする。

```text
シャトル{箱数}箱購入しました。{拠点}{筒数}筒、{拠点}{筒数}筒です。
```

例：

```text
シャトル1箱購入しました。豊中6筒、吹田4筒です。
シャトル1箱購入しました。豊中10筒です。
シャトル2箱購入しました。豊中10筒、吹田10筒です。
シャトル1箱購入しました
シャトル1箱購入しました豊中6吹田4
1箱購入しました。豊中6筒、吹田4筒です。
```

- 箱数は1以上の整数とする
- 購入配分は1筒単位の正の整数とする
- 拠点配分を省略した場合は、購入した全筒を豊中へ配分する
- 豊中または吹田の一方だけへ全量を配分してもよい
- 同じ拠点を1メッセージ内で重複指定しない
- 配分の合計は `箱数 × 10筒` と一致しなければ登録しない
- 先頭の `シャトル`、配分の `筒`、拠点間の区切り、文末の `。` は省略できる
- 購入配分は各拠点のニュー残量へ加算する
- 購入数、1箱当たりの筒数、拠点別配分、LINEイベント情報を保存する

拠点間移動メッセージの形式は次のとおりとする。

```text
シャトルを{移動元}から{移動先}へニュー{筒数}筒セミ{筒数}筒移動しました。
```

例：

```text
シャトルを豊中から吹田へ2筒移動しました。
シャトルを吹田から豊中へセミ0.5筒移動しました。
吹田にニュー2筒セミ1筒移動しました
豊中から吹田へ2移動しました
吹田にセミ2筒移動
```

- 移動元と移動先は豊中・吹田のいずれかとし、同じ拠点は指定できない
- 移動先だけを指定した場合は、もう一方の拠点を移動元として補完する
- ニューとセミは片方だけ、または両方を同じメッセージで指定できる
- `ニュー`・`セミ` をどちらも指定しない従来形式はニューの移動として扱う
- 指定する各移動量は0より大きい0.5筒刻みとする
- 先頭の `シャトル`、数量後の `筒`、末尾の `しました`、文末の `。` は省略できる
- ニュー・セミの各移動量を移動元の対応する残量から減算し、移動先の対応する残量へ加算する
- 移動元のニュー・セミのいずれかの残量が不足する場合は登録しない
- 移動日時にはLINEイベントの `timestamp` を使用する
- フェーズ9では購入と移動を履歴として保存し、Reportの残量値自体は書き換えない
- 購入・移動メッセージの送信取消を受信した場合は、対応する記録を削除する
- 履歴はWebの `/history` へ統合し、全て・報告・購入・移動の種類で切り替える
- 全て・報告・購入は全体・豊中・吹田で絞り込める。移動履歴は常に両拠点に関係するため、拠点絞り込みを選択不可にする
- シャトル報告履歴は `拠点`、`ニュー`、`セミ`、`登録元`、`日時`、`編集` を項目名付きで表示する
- 購入履歴は箱数・合計筒数・拠点別配分・登録元・日時に加え、その購入直後の両拠点のニュー・セミ残量を表示する
- 移動履歴は移動元・移動先・ニュー移動量・セミ移動量・登録元・日時に加え、その移動直後の両拠点のニュー・セミ残量を表示する
- 購入・移動履歴に表示する残量は、その操作までの通常報告・購入・移動を時系列に適用して算出し、後続の操作によって過去カードの結果を変えない
- DB取得を伴うWebページ遷移中は `読み込み中...` を表示し、履歴の種類・拠点切り替えでは押したボタン上にも待機状態を表示する
- Webフォームの登録・更新中はボタンを `登録中...`・`更新中...` に切り替え、入力と二重送信を無効化し、次画面への遷移が完了するまで状態を維持する
- 購入・移動履歴の計算では、表示と時系列計算に必要なDB列だけを取得する

### 16.2 送信取消期限後のLINE報告削除（フェーズ9）

削除対象のLINE報告へリプライして、次のいずれかを送信する。

```text
シャトル報告削除
報告削除
削除
```

引用元が同じ許可グループのLINE報告である場合だけ、DB上のReportを削除する。コマンドだけを送信した場合や、Web報告・削除済み報告・別グループの報告を引用した場合は削除しない。

### 16.3 購入・移動を反映した現在残量（フェーズ9）

各拠点の現在残量は、拠点ごとの最新Reportを基準値とし、そのReportより後に発生した購入・移動を反映して算出する。

- 通常のシャトル報告は、その拠点のニュー・セミ残量を新しい基準値として確定する
- 購入は指定された拠点のニュー残量へ加算する
- 移動は指定されたニュー・セミを移動元の対応する残量から減算し、移動先の対応する残量へ加算する
- 購入はセミ残量を変更しない
- 拠点にReportが存在しない場合はニュー・セミとも0を基準とし、購入・移動を反映する
- Report、購入、移動が削除された場合は、残っている履歴から現在残量を再計算する
- 通常報告・購入・移動の登録成功返信には、処理後の豊中・吹田の現在残量を表示する
- `シャトル残量`・`残量` とWebホームも、同じ計算結果を表示する
