## 3. 進行ルール

- 同じローカルプロジェクト内で、フェーズごとに新しいCodexタスクを作成する
- 原則としてフェーズを順番に進め、同じファイルを複数タスクで同時編集しない
- MVP完了までは `feature/line-integration` ブランチを使用する
- 各フェーズ開始時に `git status` を確認する
- 各フェーズでは対象外の機能へ着手しない
- 各フェーズ終了時にLint、型チェック、必要なテスト、production buildを実行する
- Codexには原則としてコミットさせず、利用者が差分を確認してからコミットする
- 仕様変更が発生した場合は、コードより先に `docs/line-mvp.md` または本書を更新する
- 秘密情報をコード、Markdown、Git履歴へ記録しない
- PostgreSQL移行時に既存SQLiteデータは引き継がない

### フェーズ2：PostgreSQL・Prismaデータモデル

状態：**完了**

目的：

外部公開環境でLINE Webhookから永続的にデータを保存できるDB基盤を作る。

PostgreSQL移行方針：

- マネージドPostgreSQLにはNeonを使用する
- アプリ実行時は `DATABASE_URL`、migration実行時は `DIRECT_URL` を使用する
- Neonではアプリ用にpooled接続、migration用にdirect接続を設定する
- 開発用DBは本番用とは別のNeon projectまたはbranchとして作成する
- 開発用Neon projectは `shuttle-manager-dev`（PostgreSQL 17、Singapore）を使用する
- Neon Authは使用しない
- 既存SQLiteデータは移行しない
- 既存SQLite migrationは `prisma/migrations/` に保存したまま残す
- PostgreSQL migrationは `prisma/migrations-postgresql/` で新しく管理する

実装内容：

1. 使用するマネージドPostgreSQLを決定する
2. 開発用PostgreSQLデータベースを作成する
3. `DATABASE_URL` をローカル環境変数へ設定する
4. Prisma datasourceをSQLiteからPostgreSQLへ変更する
5. SQLite用migrationをPostgreSQLへ適用しないよう整理する
6. PostgreSQL用の初期migrationを作成する
7. `ReportSource` enumを追加する
8. `Report` にLINE連携用フィールドと `reportedAt`、`updatedAt` を追加する
9. `WebhookReceipt` モデルを追加する
10. ホームと履歴の並び順を `reportedAt` 基準へ変更する
11. 空のPostgreSQL上で既存画面が動作することを確認する

注意事項：

- 現在のSQLite migrationにはSQLite専用SQLが含まれるため、そのままPostgreSQLへ適用しない
- 既存の `prisma/dev.db` のデータは移行しない
- migration履歴やSQLiteファイルを削除・移動する前に、対象を確認する
- DB接続情報をGitへコミットしない

### フェーズ9：誤報告の削除改善・購入管理（MVP後）

状態：**MVP後**

主な内容：

- 送信取消期限後もLINEからDB上の誤報告を削除できる引用返信コマンド
- Web履歴からのReport削除方法と、削除権限の決定
- `シャトル1箱購入しました。` の解析
- Purchaseモデル
- 箱当たり筒数の保存
- 保管場所の選択
- 購入履歴表示

LINEからの削除方針：

1. 誤った報告メッセージを長押ししてLINEの「リプライ」を選び、`シャトル報告削除` と送信する
2. Webhookの `quotedMessageId` とReportの `lineMessageId` を照合して、引用元のReportを特定する
3. 許可済みLINEグループ内では、報告者本人に限定せず、グループメンバーが引用したLINE報告を削除できるようにする
4. Reportの `lineGroupId` がコマンド送信元の許可済みグループIDと一致することを必須とし、他グループのReportは削除しない
5. 引用元がない場合、Web報告、削除済みの報告は削除せず、操作方法または削除できない理由を返信する
6. WebhookReceiptとReport削除を同じtransactionで処理し、Webhook再送で削除処理と返信を重複させない
7. Reply APIで削除結果を返信し、LINE上の元メッセージ自体は残ることを案内する
8. 削除後は、次に新しいReportを各画面と `シャトル残量` の最新値として扱う

Web履歴からの削除方針：

1. 誤操作を避けるため、削除ボタンは履歴一覧ではなく編集画面に置き、確認操作を必須にする
2. `DELETE /api/report/[id]` を追加し、存在しないReportにはHTTP 404を返す
3. 最新Reportを削除した場合は、次に新しいReportを最新値として表示する
4. 認証なしの公開画面に削除機能を追加しない。フェーズ9開始時に、削除に必要な最小限のアクセス制御を先行実装するか、Web削除をフェーズ11まで延期するか決定する

削除改善のテスト方針：

- 許可済みグループのメンバーが、本人または他のメンバーのLINE報告へ引用返信すると対象Reportを削除する
- 引用元がない場合、未許可グループ、別グループのReportでは削除しない
- Webhook再送で削除処理と返信を重複させない
- Web削除を実装する場合は、未認証の削除、存在しないReport、二重操作、最新値の切り替わりを確認する

購入管理へ着手する前に削除改善の権限方針を決定する。購入管理については、1箱の筒数、購入品の保管場所、共通倉庫の扱いも決定する。
